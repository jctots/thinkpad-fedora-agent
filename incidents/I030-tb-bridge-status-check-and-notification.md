## I030 — 2026-08-28 — no standing check on host state between sessions, generalized into a health-check runner

**Area:** agent

**Symptom:** Second-brain agent reported a request timeout on its thunderbird
MCP call. Host-side investigation (this session) found `tb-bridge.service`
actually healthy at the time — active, extension connected, Betterbird
running, auth working correctly (401 on unauthenticated request). Along the
way, checked whether `TB_AUTH_TOKEN` in `~/.config/thunderbird-cli/bridge-daemon.env`
(regenerated by I029) matched what `~/.local/bin/tb-mcp-authed` actually
sources — per D153 that wrapper reads `~/.config/second-brain/second-brain.env`,
a separate file `docs/thunderbird-cli.md` didn't mention. A hash comparison
showed the two `TB_AUTH_TOKEN` values differed; the user confirmed after the
fact that the tokens already matched and mail access was working, so no fix
was needed there — `docs/thunderbird-cli.md` has since been corrected to
describe the D153 layout.

Separately, established that `tb-bridge.service` is deliberately `static`
(no `[Install]`), started on demand by `betterbird-with-bridge` paired to
Betterbird's own launch — never at boot or login. So I029's failure mode
(crash-looping on a missing env file) could recur silently for hours with
nothing surfacing it, exactly as happened in I029 itself.

**Cause:** No standing check existed between sessions for tb-bridge or, once
raised, for anything else host-state-related (pending updates, fprintd's
I015 crash-loop pattern, battery drain).

**Fix:** Built a generic, pluggable health-check runner rather than a
tb-bridge-only script (the user's explicit ask, after the first version
landed):

- `scripts/system-health-check.sh` (base layer) — `run` executes every
  check module under `scripts/health-checks/*.sh` (machine-generic) and
  `hosts/thinkpad-e14-gen5/health-checks/*.sh` (host-specific quirks).
  Check contract: exit 0 = healthy (silent), exit 1 = alert (stdout becomes
  the `notify-send` body), anything else = the check script itself is
  broken and is reported as such. Every run's full output is logged to
  `~/.local/state/system-health-check/<name>.log` regardless of outcome —
  specifically so that when the user gets notified, the agent can read the
  verbose detail straight off disk instead of working from the terse
  notification text or re-running anything. `install` writes/enables
  `system-health-check.timer` (`OnBootSec=5min`, `OnUnitActiveSec=15min`),
  same shape as `scripts/install-kopia-backup.sh`.
- `hosts/thinkpad-e14-gen5/health-checks/tb-bridge.sh` — the original
  check, migrated: alerts only on the unit `failed`, or Betterbird running
  with the bridge not active.
- `hosts/thinkpad-e14-gen5/health-checks/fprintd.sh` — same failed-unit
  detection shape, applied to I015's crash-loop pattern (fprintd's
  Restart=on-failure drop-in still has systemd's default start-limit, so a
  fast enough loop ends in `failed`, readable without root).
- `hosts/thinkpad-e14-gen5/health-checks/battery-drain.sh` — alerts on
  sustained high discharge (>35W, a first-pass guess documented as such,
  not a measured baseline) for 2 consecutive 15-minute checks, only while
  actually discharging. Prompted by the user asking how fast the battery
  was draining right now (found: 24.5W at the time, explained by several
  concurrently-open apps, not a bug).
- `scripts/health-checks/pending-updates.sh` (base layer) — reuses the
  same read-only `rpm-ostree upgrade --check` / `flatpak update` (answered
  "n") queries `scripts/update-check.sh` already uses. Deliberately does
  *not* alert on "an update exists" (that would fire most days); tracks how
  long one has sat unapplied in a state file and only alerts past 7 days.

**Explicitly left out — etckeeper drift.** `scripts/etc-drift.sh` needs
`pkexec` to read `/etc`'s git state (`/etc/.git` is `root:root`, mode
`700`). CLAUDE.md's root-command model is a double gate: Claude Code's own
per-call approval fires first, then the polkit dialog. An unattended
systemd timer has no Claude Code session in the loop at all — wiring this
in would mean an unattended `pkexec` popping a real polkit auth dialog
every 15 minutes with nothing gating it, which is both worse UX than the
on-demand `/etc-drift` skill it would nominally replace and a quiet
workaround of a guardrail this repo is explicit about not routing around.
Raised to the user directly rather than building it silently; kept as the
existing on-demand skill, unchanged.

Verified: all four check modules run clean individually and via the
runner; full alert path (fake failing check) confirmed the notification
fires and the summary/per-check logs record it; timer installed with a
confirmed next-run time.

**Tried first:** First proposal (for the original tb-bridge-only version)
was to have this session's own `ScheduleWakeup`/`CronCreate` re-wake itself
periodically and run the check inline, optionally escalating to a `haiku`
subagent for cheapness. User pushed back: those mechanisms re-wake *this*
session under its own model (no override), a subagent has its own fixed
spin-up overhead for a check this trivial, and blending the check's cost
into this session's usage makes it impossible to cleanly measure whether
the mechanism is worth keeping. Landed on a pure-bash systemd timer with
zero LLM involvement for the common case, notification-only — the user
checks in with the agent themselves only when notified, no automated relay
step at all.

**Reversibility:** `/var/home` layer — script files plus two systemd
`--user` unit files (the old tb-bridge-only ones were removed as part of
this), all plain home-directory state, trivially removable
(`systemctl --user disable --now system-health-check.timer` + delete the
unit files, the runner, and the check-module directories).

**Captured in:** `scripts/system-health-check.sh`,
`scripts/health-checks/`, `hosts/thinkpad-e14-gen5/health-checks/`

**Tally:** time-to-fix ~1h10m (spans the original tb-bridge-only version
and the generalization requested after) · first proposal: ✗ (agent-loop
idea rejected in favor of the plain-bash-timer approach)
